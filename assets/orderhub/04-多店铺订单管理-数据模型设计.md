## 4. 订单状态机



```
待审核 ──审核通过──→ 待发货 ──发货+回传单号──→ 已发货 ──买家确认/超时──→ 已完成

&#x20; │                    │                           │

&#x20; ├─审核拒绝/买家取消──→ 已取消                    └─退款──→ 已取消

&#x20; │                    │

&#x20; └─（缺货/地址异常）──→ 异常 ──调拨补货/地址修正──→ 待发货

&#x20;                             └─无法处理──→ 已取消
```

状态流转触发点（对应原型交互）：



* 审核：订单同步后自动 / 手动审核

* 预警：发货前库存比对触发「异常 - 缺货」

* 发货：批量发货页打单成功 → 回传单号 → 状态置为已发货

* 取消：买家取消 / 审核拒绝 / 异常无法处理



***

## 5. 设计决策（面试可讲）



1. **订单明细存 SKU / 价格快照**：订单是事实记录，不能随商品表改价 / 改名而变；这是电商系统的标准做法。

2. **inventory 一商品一行 + 比对告警**：不做实时锁库存，用 available\_qty 与在途订单比对触发预警 ——MVP 用最小成本解决「超卖」这一最高发风险，架构上可平滑升级到锁定机制。

3. **orders 冗余 platform 字段**：平台维度是最高频筛选条件，冗余字段避免高频 JOIN，是 B 端表设计常见的反范式取舍。

4. **预留 api\_status**：店铺表保留平台 API 对接状态字段，为未来接入 Shopee/Lazada/TikTok 开放平台留好架构位置（个人暂无法申请，但设计上可见前瞻性）。

5. **币种下放到店铺与订单级别**：跨境场景多币种是刚需（MYR/THB/SGD/VND），不做全局统一币种假设。

6. **operation\_logs 独立成表**：对应原型的操作时间线，同时满足风控审计需要 —— 产品设计里「留痕」是 B 端系统的隐性需求。

## 6. 附录：SQLite 建表 SQL（可直接执行）



```
CREATE TABLE users (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; username TEXT UNIQUE NOT NULL,

&#x20; password\_hash TEXT NOT NULL,

&#x20; email TEXT UNIQUE,

&#x20; display\_name TEXT NOT NULL,

&#x20; role TEXT NOT NULL DEFAULT 'owner',

&#x20; created\_at TEXT NOT NULL

);

CREATE TABLE shops (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; user\_id INTEGER NOT NULL REFERENCES users(id),

&#x20; platform TEXT NOT NULL,

&#x20; shop\_name TEXT NOT NULL,

&#x20; country TEXT NOT NULL,

&#x20; currency TEXT NOT NULL,

&#x20; api\_status TEXT DEFAULT 'unlinked',

&#x20; status TEXT DEFAULT 'active',

&#x20; created\_at TEXT NOT NULL,

&#x20; UNIQUE(user\_id, platform, shop\_name)

);

CREATE TABLE products (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; user\_id INTEGER NOT NULL REFERENCES users(id),

&#x20; sku TEXT NOT NULL,

&#x20; product\_name TEXT NOT NULL,

&#x20; category TEXT,

&#x20; cost\_price REAL,

&#x20; status TEXT DEFAULT 'on',

&#x20; created\_at TEXT NOT NULL,

&#x20; UNIQUE(user\_id, sku)

);

CREATE TABLE inventory (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; product\_id INTEGER UNIQUE NOT NULL REFERENCES products(id),

&#x20; total\_qty INTEGER NOT NULL DEFAULT 0,

&#x20; available\_qty INTEGER NOT NULL DEFAULT 0,

&#x20; on\_the\_way INTEGER DEFAULT 0,

&#x20; safety\_stock INTEGER DEFAULT 0,

&#x20; updated\_at TEXT

);

CREATE TABLE orders (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; order\_no TEXT NOT NULL,

&#x20; shop\_id INTEGER NOT NULL REFERENCES shops(id),

&#x20; platform TEXT NOT NULL,

&#x20; buyer\_name TEXT,

&#x20; buyer\_country TEXT,

&#x20; buyer\_phone TEXT,

&#x20; address TEXT,

&#x20; currency TEXT NOT NULL,

&#x20; total\_amount REAL NOT NULL,

&#x20; status TEXT NOT NULL,

&#x20; abnormal\_type TEXT,

&#x20; shipped\_at TEXT,

&#x20; created\_at TEXT NOT NULL,

&#x20; updated\_at TEXT

);

CREATE INDEX idx\_orders\_shop ON orders(shop\_id);

CREATE INDEX idx\_orders\_status ON orders(status);

CREATE TABLE order\_items (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; order\_id INTEGER NOT NULL REFERENCES orders(id),

&#x20; product\_id INTEGER REFERENCES products(id),

&#x20; sku TEXT NOT NULL,

&#x20; product\_name TEXT NOT NULL,

&#x20; quantity INTEGER NOT NULL,

&#x20; unit\_price REAL NOT NULL,

&#x20; subtotal REAL NOT NULL

);

CREATE TABLE settlements (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; shop\_id INTEGER NOT NULL REFERENCES shops(id),

&#x20; platform TEXT NOT NULL,

&#x20; period TEXT NOT NULL,

&#x20; settlement\_no TEXT,

&#x20; total\_sales REAL,

&#x20; platform\_fee REAL,

&#x20; shipping\_fee REAL,

&#x20; refund\_amount REAL,

&#x20; net\_amount REAL,

&#x20; status TEXT DEFAULT 'pending',

&#x20; checked\_at TEXT,

&#x20; UNIQUE(shop\_id, period)

);

CREATE TABLE operation\_logs (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; order\_id INTEGER NOT NULL REFERENCES orders(id),

&#x20; action TEXT NOT NULL,

&#x20; operator TEXT,

&#x20; detail TEXT,

&#x20; created\_at TEXT NOT NULL

);
```
